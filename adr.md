# ADR — Единый архитектурный реестр (`architecture-registry`)

**Что это за документ.** Запись архитектурных решений (Architecture Decision Record) по
**фактическому состоянию** системы: описываются решения, которые уже реализованы, развёрнуты
и проверены на стенде. 

| Параметр | Значение |
|---|---|
| Дата фиксации | 08.10.2026 |
| База фиксации | ветка `main`, коммит `335c047` (рабочее дерево чистое) |
| Стенд | 4 контейнера `docker-compose.yml`: `arch-registry-db`, `arch-registry-backend`, `arch-registry-frontend`, `arch-diagrams-module` |
| Источники фактов | файлы репозитория; `sql/01_ddl.sql`…`06_seed_addresses.sql`; `docker-compose.yml`; живая база `architecture_registry`; живой API модуля схем (`http://localhost:8082`) |
| Статус | **Accepted as-is** — документ описывает систему «как реализовано» |
| Проверяемость | все утверждения подтверждаются командами из §10 |

Статусы решений: `Accepted` — реализовано и работает; `Accepted (ограничение)` — реализовано
сознательно ограниченно; `Deferred` — осознанно не реализовано (см. §9).

## 3. Решения по данным реестра

### ADR-001. PostgreSQL — единственное хранилище истины; снапшот версии — дополнение

**Контекст.** Реестр и визуализация должны читаться из одного источника; при этом для
воспроизводимости опубликованной схемы нужен снимок.

**Решение.** Физическая модель реестра v2.0 — таблицы PostgreSQL (`sql/01_ddl.sql`):
`information_system`, `application_module`, `environment`, `module_instance`,
`module_deployment`, `server`, `cluster`, `network_zone`, `network_segment`, `router`,
`firewall`, `network_interface`, `protocol`, `information_flow`, `information_flow_project`,
`project`, `audit_log`; представления `V01`…`V16` (`sql/02_views.sql`). Диаграммный слой
хранится в отдельных таблицах в **той же** СУБД (`architecture_diagram`,
`architecture_diagram_element`, `architecture_diagram_relationship`, `diagram_version`),
`diagram_version.snapshot_json` — неизменяемый JSON-снапшот версии.

**Следствия.**
* Реляционная модель отвечает за поиск, связи и ссылочную целостность, снапшот — за
  воспроизводимость опубликованной версии; дублирования «двух истин» нет.
* СУБД одна: и реестр, и схемы читаются одним соединением, синхронизация между хранилищами не нужна.
* Ограничение: снапшот не индексируется — выборки «по снапшотам» не поддерживаются.

**Подтверждение.** `sql/01_ddl.sql`, `sql/02_views.sql`, `architecture-diagrams/server/schema.sql`,
`db.js`, `diagrams.js` (`publishDiagram` пишет `snapshot_json`).

### ADR-002. Информационный поток — на уровне модулей

**Контекст.** Требования описывали поток со ссылкой на экземпляр модуля; фактическая модель v2.0
описывает поток между **модулями** и не содержит адресов.

**Решение.** `information_flow(source_module_id, target_module_id, protocol_id, source_port,
target_port, status, valid_from, valid_to)`; задействованность в проекте — через
`information_flow_project`. Экземпляры и адреса в самой сущности потока отсутствуют;
физический смысл («с какого адреса на какой») выводится из размещений сторон (ADR-020).

**Следствия.**
* Схема Container строится прямо из потоков между модулями, Deployment — агрегирует потоки
  уровня модулей в связи между размещениями.
* Один логический поток может породить несколько физических связей (несколько размещений
  на среду); модуль агрегирует их в одну связь с подписью.
* Поток не привязан к среде: состав схемы развертывания определяется размещениями
  (ADR-003) — действующими размещениями **среды схемы** (ADR-026).

**Подтверждение.** `sql/01_ddl.sql`, `architecture-diagrams/README.md` («Важное расхождение
с текстом ТЗ»), `server/graph.js` (`flowDeploymentEdges`, `generateContainer`, `generateDeployment`).

### ADR-003. Среда — атрибут экземпляра модуля

**Контекст.** Требование §6 ТЗ v1.0 предлагало хранить `environment_id` в размещении;
в реестре v2.0 среда закреплена за экземпляром (`module_instance.environment_id NOT NULL`,
уникальность `(module_id, environment_id, name)`).

**Решение.** Среда остаётся у экземпляра. Размещение (`module_deployment`) хранит только
уточняющие измерения: целевой узел (`server_id` **или** `cluster_id`, ровно одно поле),
роль, состояние (`deployment_role`, `deployment_state`), период (`valid_from`, `valid_to`).
Среда схемы развертывания — параметр области самой схемы
(`architecture_diagram.scope_environment_id`): схема описывает размещения одной среды
(ADR-026), а контуром служит сетевой сегмент узла размещения (ADR-025).

**Следствия.**
* Невозможно состояние «экземпляр в PROD, размещение в TEST»: расхождение устранено моделью,
  а не проверкой.
* Валидация сверяет среду размещения со средой схемы: `ENVIRONMENT_SCOPE_MISMATCH`
  (WARNING — размещение относится к другой среде), а отсутствие среды у схемы развертывания —
  `ENVIRONMENT_SCOPE_MISSING` (ERROR — публикация блокируется, ADR-026).
* Дублирующий атрибут не введён; замечание Б2 протокола замечаний закрыто выбором действующей модели.

**Подтверждение.** `sql/01_ddl.sql` (07. `module_deployment`), `server/validate.js`
(`ENVIRONMENT_SCOPE_MISSING`, `ENVIRONMENT_SCOPE_MISMATCH`),
`docs/requirements-review-deployment-diagrams-v1.0.md` (Б2). Среда экземпляра остаётся в силе —
`module_instance.environment_id NOT NULL`; среду схемы хранит `architecture_diagram.scope_environment_id`
(ADR-026).

### ADR-004. Сетевой адрес развертывания — `network_interface`

**Контекст.** Требования §7 вводили отдельные сущности `server_network_address` и
`cluster_network_address`; в реестре адрес устройства уже описан таблицей `network_interface`.

**Решение.** Единственная таблица адресов — `network_interface` с CHECK-ограничением
«ровно один владелец» из `server_id`, `router_id`, `firewall_id`, `cluster_id`:
* адрес устройства — роль `SERVICE`, `MANAGEMENT`, `VIRTUAL`, `BACKUP`, `OTHER`;
* адрес кластера — тот же интерфейс с `cluster_id` и ролью из словаря `INGRESS` / `NODE` /
  `MANAGEMENT` (CHECK `chk_network_interface_cluster_role`); адресов у кластера может быть
  несколько (точка входа, узлы, управление);
* `environment_id` интерфейса — среда адреса (`NULL` — действует во всех средах узла);
* `network_segment_id` — контур адреса (необязателен);
* `cluster.management_address` сохранён как резервный источник адреса управления, если у
  кластера ещё не заведено ни одного интерфейса.

**Следствия.**
* Отдельной сущности «адрес кластера» нет — есть интерфейс с владельцем-кластером; страница
  «Сетевые интерфейсы» (раздел меню «Инфраструктура») — единственное место ввода адресов.
* Представления `v15_deployment_addresses`, `v15a_instance_primary_address`, `v16_flow_addresses`
  дают «адрес размещения» и «поток с адресами»; приоритет адреса: `SERVICE → INGRESS →
  VIRTUAL → NODE → MANAGEMENT → BACKUP → OTHER`, внутри роли — по возрастанию IP.
* Миграция `sql/05_network_addresses.sql` переносит адреса кластеров и удаляет старую таблицу,
  поэтому сразу после неё переприменяется `02_views.sql`.
* Замечание Б3 протокола закрыто: адрес кластера отображён на `network_interface` без
  изменения модели реестра.

**Подтверждение.** `sql/01_ddl.sql` (12. `network_interface`), `sql/05_network_addresses.sql`,
`sql/02_views.sql` (`V15`…`V16`), `server/registry.js` (`getDeploymentAddresses`,
`ADDRESS_ROLE_PRIORITY`), `sql/verify_addresses.sql`, `sql/README.md`.

## 4. Решения по модулю «Архитектурные схемы»

### ADR-005. Реестр — источник истины, схема — представление

**Контекст.** Схема должна объяснять реестр и не создавать второй набор архитектурных данных.

**Решение.** Сервер модуля читает нормализованную модель реестра напрямую из PostgreSQL
(`server/registry.js`) и **не изменяет** её: все запросы — `SELECT`. Собственные данные модуля —
только диаграммный слой (позиции, подписи, ссылки). Ссылка на объект реестра хранится как
`registry_object_type` + `registry_object_id` (в графе — `registryRef`), атрибуты объектов в
схему не копируются.

**Следствия.**
* Реестр можно менять через основное приложение — схема подтянет изменения при `SYNC`/`REBUILD`.
* DDL реестра не модифицируется модулем: контейнер `diagrams` самодостаточен; менять
  `sql/01_ddl.sql` и образ БД при доработках модуля не требуется.
* backend реестра не является runtime-зависимостью модуля: генерация схемы не делает
  синхронных REST-вызовов к нему (десятки запросов выполняются одним соединением с БД).

**Подтверждение.** `server/db.js`, `server/registry.js`, `server/schema.sql`, README модуля
(«Границы реализации»).

### ADR-006. Модуль — отдельный контейнер и отдельный табличный слой с само-миграцией

**Контекст.** Требования позволяли «существующая СУБД + JSON snapshot»; нужно было встроить
визуализацию, не переписывая frontend и БД реестра.

**Решение.** Сервис `diagrams` (Node 18) в одном контейнере отдаёт и REST API, и собранное SPA
(React + `@xyflow/react`), хранит свой слой в таблицах `architecture_diagram*`. При старте
сервис идемпотентно выполняет `server/schema.sql` (`migrate.js`) с повторами, чтобы контейнер
поднимался и при медленном старте СУБД; SPA отдаётся с префиксом `APP_BASE`
(по умолчанию `/diagrams-module`) и одновременно в корне своего порта.

**Следствия.**
* Развёртывание модуля — один сервис в том же compose; ручная миграция не нужна.
* Диаграммные таблицы изолированы от таблиц реестра (в т. ч. от аудита: `architecture_diagram*`
  в список `audited_tables` не входят — аудитируется только реестр, ADR-017).
* В compose `depends_on: db: service_healthy` — миграция ждёт готовности PostgreSQL.

**Подтверждение.** `architecture-diagrams/Dockerfile`, `server/index.js` (`start()`), `server/migrate.js`,
`server/schema.sql`, `docker-compose.yml` (сервис `diagrams`).

### ADR-007. Внутренняя графовая модель — единственный источник для canvas и экспорта

**Контекст.** Схема отображается в редакторе и выгружается в 6 форматов; расхождение между
«тем, что видно» и «тем, что выгружено» недопустимо.

**Решение.** Сервер формирует внутреннюю графовую модель (`schemaVersion`, `nodes[{id,
registryRef, c4Type, parent, name, technology, description, position, size, style}]`,
`edges[{id, source, target, registryRef, label, technology}]`). Из неё строится SVG, PlantUML,
Mermaid, JSON, и она же отдаётся клиенту для canvas (`ArchNode`/`ArchEdge` на клиенте —
зеркало серверной структуры). Стабильные идентификаторы: узел — `тип:uuid` реестрового
объекта, связь — `information_flow:uuid`, связь развертывания — `dep:{размещение}->{размещение}`.

**Следствия.**
* Экспорт не зависит от состояния canvas: PNG/PDF берут серверный SVG (ADR-015).
* Идентификаторы связей развертывания считает одна функция `flowDeploymentEdges`
  (`server/graph.js`), поэтому canvas, панель «Потоки области» и отчёты согласованы.
* Клиент не является генератором семантики: он меняет позиции, подписи и состав, но не
  пересчитывает объекты реестра.

**Подтверждение.** `server/graph.js` (`makeNode`, `makeEdge`, `nodeKey`, `edgeKey`,
`deploymentEdgeId`, `flowDeploymentEdges`), `server/exporter.js`, `src/model/diagramTypes.ts`.

### ADR-008. Нотация C4 и фиксированный маппинг объектов реестра

**Контекст.** Реестр не является C4-моделью; маппинг нужно закрепить, иначе схемы будут
трактоваться по-разному.

**Решение.** Реализованы три типа схем (`diagram_type`): `SYSTEM_CONTEXT`, `CONTAINER`,
`DEPLOYMENT`. Маппинг: `information_system → SoftwareSystem` (или `SystemBoundary` для области
«проект»), `application_module → Container`, `module_instance`/`module_deployment` →
`DeploymentInstance`, `server`/`cluster` → `DeploymentNode`, `environment` →
`EnvironmentBoundary`, `information_flow → Relationship`, `protocol` → technology связи,
`project → SystemBoundary`. Типовые размеры карточек заданы в `SIZE` (`graph.js`) и продублированы
визуальными вариантами (`primary`, `application`, `external`, `infrastructure`, `boundary`).

**Следствия.**
* Связи System Context агрегируются между системами (`потоков: N` + протоколы), Container
  строится по потокам модулей, Deployment — по размещениям в срезе.
* `DeploymentInstance` в схеме развертывания — это **размещение** (`module_deployment`): именно
  оно несёт адрес и узел (см. ADR-011, ADR-020).
* Тип схемы проверяется на входе: неизвестный `diagramType` → HTTP 400.

**Подтверждение.** `server/graph.js` (`C4_TYPE`, `SIZE`, `GENERATORS`, `generateGraph`),
`src/model/c4Types.ts`, `GET /api/meta` (`diagramTypes`).

### ADR-009. Автогенерация: `REBUILD` и `SYNC`

**Контекст.** Схема должна обновляться по реестру, но ручная компоновка — данные пользователя.

**Решение.** `POST /api/diagrams/{id}/generate` принимает `mode`:
* `REBUILD` — полная перестройка, включая раскладку; применяется при создании схемы, смене
  среза и по явному запросу пользователя;
* `SYNC` — сохраняет существующие позиции (`existingPositions`), обновляет состав и атрибуты.
Локальная кнопка «Авто-раскладка» (`localLayout` в `src/layout/layoutService.ts`) пересчитывает
позиции на клиенте без обращения к реестру.

**Следствия.**
* Сервер остаётся единственным местом, где граф строится по данным реестра; клиентская
  раскладка работает на уже загруженном графе и реестр не перечитывает.
* Состояние `PUBLISHED` при записи результата генерации переводится в `DRAFT`
  (генерация — это правка схемы).
* `dependencies_dirty` сбрасывается в `false` при сохранении/генерации (флаг «есть изменения
  зависимостей»).

**Подтверждение.** `server/graph.js` (`generateGraph`, `applyLayout`), `server/diagrams.js`
(`applyGeneratedGraph`, `saveGraph`, `setDependenciesDirty`), `src/layout/layoutService.ts`
(`localLayout`, `localDeploymentLayout`).

### ADR-010. Область схемы и срез по среде

**Контекст.** Схемы нужны и «по одной ИС», и «в разрезе проекта»; схемы развертывания — ещё и
в разрезе среды (прод/тест отдельно).

**Решение.** `architecture_diagram.scope_type` + `scope_object_id` поддерживают
`information_system` и `project`. Для проекта в схему попадают **все** информационные потоки
проекта (`information_flow_project`) и все модули, участвующие в этих потоках. Среда схемы
развертывания — `architecture_diagram.scope_environment_id`: схема описывает размещения одной
среды, меняется через `PATCH /api/diagrams/{id}/environment`, граф при смене перестраивается
(`REBUILD`).
*(история: ADR-025 снял разрез по среде как механизм — колонка, эндпоинт `PATCH …/slice` и селектор
были удалены; ADR-026 вернул среду обязательным параметром области (другой эндпоинт), а контуром
схемы остался сетевой сегмент. Область схемы — ИС **или** проект — не менялась.)*

**Следствия.**
* Область задаёт контекст загрузки (`loadScope`), поэтому все три генератора работают и по ИС,
  и по проекту.
* Среда влияет только на схемы развертывания: учитываются действующие размещения выбранной среды
  (ADR-026); у схем контекста и контейнеров среда не заполняется.
* Смена среды перезаписывает раскладку — ручные позиции при этом теряются осознанно
  (схема строится заново по данным реестра).

**Подтверждение.** `server/graph.js` (`SCOPE_TYPES`, `loadScope`, `generateGraph`),
`server/diagrams.js` (`SCOPE_TYPES`, `createDiagram`, `updateDiagramEnvironment`),
`server/schema.sql` (`scope_environment_id`), `server/index.js`
(`PATCH /api/diagrams/{id}/environment`), `frontend/src/pages/DiagramsPage.tsx`,
`src/pages/DiagramListPage.tsx`, `src/editor/DiagramToolbar.tsx`.
*(`updateDiagramSlice` и `PATCH …/slice` из ADR-025 не возвращались: смена среды выполняется
эндпоинтом `PATCH …/environment`.)*

### ADR-011. Узел размещения — контейнер: рамка растёт под состав, экземпляры всегда внутри

**Контекст (проблема, из-за которой решение принято).** Схема развертывания читается по
уровням «контур → узел размещения → экземпляр» *(ADR-025: контуром схемы стал сетевой сегмент
узла размещения; до ADR-025 контуром был контур среды, ADR-010)*. До этого решения узлы размещения были
карточками фиксированного размера, а экземпляры располагались отдельно от них: на реальных
данных 8 из 8 экземпляров схемы `di1` лежали **вне** рамок своих узлов, а схема `dep2`
(PUBLISHED) до сих пор показывает 8 нарушений `INSTANCE_OUTSIDE_NODE` — так выглядит геометрия,
сохранённая до введения правила.

**Решение.** Один инвариант, действующий на всех уровнях модуля:

```
рамка узла размещения = max(270 × 120, габариты состава + отступ 16 px по правому/нижнему краю)
«шапка» узла        = 84 px (имя, технология, адреса развертывания, счётчик состава, статус)
экземпляры          = сетка внутри рамки: 1 колонка до 3 экземпляров, 2 — до 8, иначе 3
притягивание        = x ≥ node.x + 16 (padding), y ≥ node.y + 84 (шапка)
позиция узла        = координата пользователя и не смещается (рамка растёт только вправо/вниз)
```

Реализация распределена по слоям так, чтобы инвариант нельзя было нарушить ни одним путём:

| Слой | Файл | Что обеспечивает |
|---|---|---|
| Генерация и раскладка | `server/layout.js` | `containerFrame`, `packContainerChildren`, `normalizeContainers`, `deploymentLayout` |
| Серверный граф | `server/graph.js` | `applyLayout`: для схемы развертывания размеры берутся из раскладки, затем `normalizeContainers` (в т. ч. в режиме `SYNC`) |
| Запись в хранилище | `server/diagrams.js` | `writeGraph` нормализует состав при сохранении — в БД не бывает экземпляров вне узла |
| Экспорт | `server/exporter.js` | рамка узла пересчитывается по составу (`buildBoxes`), экземпляры рисуются поверх рамки по глубине вложенности; PlantUML — вложенный блок, Mermaid — `subgraph` |
| Клиентский canvas | `src/layout/layoutService.ts`, `src/editor/DiagramEditor.tsx` | `normalizeContainers`, `reparentInstances`, `fitContainers`, клампинг при перетаскивании, каскадное перемещение узла вместе с составом |
| Валидация | `server/validate.js`, `src/validation/diagramValidator.ts` | `INSTANCE_OUTSIDE_NODE`, `INSTANCE_WITHOUT_NODE`, `NODE_FRAME_COLLAPSED` |

**Следствия.**
* Узел размещения стал настоящим контейнером C4: состав узла — часть узла, а не отдельные карточки.
* Изменение состава (перенос экземпляра, добавление/удаление размещения) само расширяет рамку —
  ручная подгонка размеров не нужна и невозможна (ADR-012).
* Перепривязка (reparent) выполняется **только** для экземпляров, которые переместил пользователь
  (`movedIds` из `resolveChanges`): перетаскивание узла двигает состав, но не меняет его
  принадлежность; экземпляр меняет узел только при собственном перетаскивании или через селект
  «Узел размещения» в панели свойств.
* Удаление узла размещения удаляет и его состав (каскад на клиенте).
* Инвариант проверяем: `di1` на 08.10.2026 — 17 узлов, 13 связей, 8 рамок, 8 экземпляров,
  **0 вне рамок**; валидация по этой схеме даёт 0 предупреждений `INSTANCE_OUTSIDE_NODE`.

**Подтверждение.** `server/layout.js`, `server/graph.js`, `server/diagrams.js`, `server/exporter.js`,
`server/validate.js`, `src/editor/DiagramEditor.tsx`, `src/layout/layoutService.ts`,
`src/nodes/NodeShell.tsx`, `README.md` модуля (раздел «Узлы размещения и их состав»).

### ADR-012. Ручные координаты — данные пользователя, размер узла — вычисляемый

**Контекст.** Пользователь расставляет схему вручную; при этом рамка узла должна следовать за составом.

**Решение.** Позиция узла — пользовательская координата, которая сохраняется и не перезаписывается
`SYNC`-синхронизацией. Размер узла размещения — **производная величина**: поля ширины/высоты в
панели свойств для узла-контейнера отключены, размер считается по составу. Для остальных узлов
(карточки, границы) размеры остаются обычными свойствами.

**Следствия.**
* Не бывает «узла с заданной вручную высотой 120 px и 5 экземплярами внутри».
* Пользователь управляет компоновкой перетаскиванием и кнопкой «Авто-раскладка»; геометрия
  контейнера всегда согласована с составом.
* Границы контуров также считаются по составу — их координата в расчёт не берётся
  (`collectBoxes`/`nodeBbox`): это относится и к контуру сетевого сегмента схемы развертывания
  (`NetworkSegmentBoundary`, ADR-025), и к ручному контуру среды (`EnvironmentBoundary`).

**Подтверждение.** `src/editor/PropertiesPanel.tsx` (отключённые размеры у контейнера),
`src/layout/layoutService.ts` (`collectBoxes`, `normalizeContainers`), `server/exporter.js` (`nodeBbox`).

### ADR-013. Валидация: авторитет — backend, на клиенте — предварительная

**Контекст.** Ошибки схемы (битые ссылки, нарушения уровней) должны блокировать публикацию и
при этом быстро подсвечиваться в редакторе.

**Решение.** Авторитетная проверка — `POST /api/diagrams/{id}/validate` (`server/validate.js`),
работающая по данным реестра (существование объектов, их статусы, протокол потока, порт,
циклы иерархии, состав узлов размещения, адреса, среда схемы развертывания и контур сетевого
сегмента, ADR-025/ADR-026). Клиентская проверка
(`src/validation/diagramValidator.ts`) — быстрая эвристика без обращения к БД: пустая схема,
битые концы связей, self-loop, циклы `parent`, инвариант узлов размещения, изолированные узлы.
Уровни: `ERROR` / `WARNING` / `INFO`; `summary.errors === 0` → `canPublish: true`.

**Следствия.**
* Публикация блокируется на сервере: `POST …/publish` при наличии ERROR отвечает `422` и
  возвращает отчёт валидации (клиентские проверки не являются защитой).
* Проблемы индексируются по узлам/связям (`buildIssueIndex`) и подсвечиваются на canvas.
* В `WARNING` попадают ситуации, которые нельзя закрыть кодом (нет адреса у узла, подпись связи
  без адресов); в `INFO` — «рамка узла не растянута под состав» для схем, сохранённых до ADR-011.

**Подтверждение.** `server/validate.js`, `server/index.js` (`/validate`, `/publish`),
`src/validation/diagramValidator.ts`, `src/editor/ValidationPanel.tsx`.

### ADR-014. Версии, публикация и optimistic locking

**Контекст.** Нужны воспроизводимость опубликованной схемы и защита от затирания чужой правки.

**Решение.** Модель состояний: `DRAFT → PUBLISHED → ARCHIVED` (в БД), при публикации создаётся
неизменяемый снапшот `diagram_version.version_no = MAX+1` со всем графом (`snapshot_json`:
`schemaVersion`, `diagramId`, `code`, `name`, `diagramType`, `scope`,
`revision`, `publishedAt`, `nodes`, `edges`) и фиксируется `published_version`.
Сохранение графа (`PUT /api/diagrams/{id}`) выполняется в транзакции с `SELECT … FOR UPDATE`
и проверкой `revision`: несовпадение → **HTTP 409**; при сохранении `PUBLISHED` переводится в
`DRAFT` (правка после публикации — новая версия, а не изменение опубликованной).
Версии читаются (`GET …/versions`, `GET …/versions/{no}`) и восстанавливаются
(`POST …/versions/{no}/restore` — это обычное сохранение, снова переводящее схему в `DRAFT`).

**Следствия.**
* Опубликованный снапшот — источник воспроизводимости: по нему можно отрисовать версию схемы
  независимо от текущего состояния реестра.
* Конкурентные правки не «сливаются молча»: второй пользователь получает 409 и должен
  перечитать схему.
* Граф диаграммы пишется одной транзакцией (узлы и связи — bulk-вставка чанками) — частично
  сохранённой схемы не бывает.

**Подтверждение.** `server/diagrams.js` (`saveGraph`, `publishDiagram`, `listVersions`,
`getVersion`), `server/index.js` (`/publish`, `/versions`, `/restore`), `architecture-diagrams/README.md`.

### ADR-015. Экспорт: тяжёлые форматы — на сервере, растровые — на клиенте

**Контекст.** Нужны SVG, PNG, PDF, PlantUML, Mermaid, JSON; добавлять headless-рендерер в
контейнер не хотелось.

**Решение.** Сервер (`server/exporter.js`) отдаёт `svg`, `plantuml` (C4-PlantUML, для
`DEPLOYMENT` включается `C4_Deployment`), `mermaid` (`flowchart LR` + `subgraph` для узлов
размещения), `json` — всё из внутренней модели. Клиент (`src/export/exportService.ts`)
растеризует тот же серверный SVG в PNG (canvas ×2) и печатает в PDF через диалог браузера.
Экспорт доступен `GET …/export?format=…`, встроенный режим — `?inline=1`; право определяется
ролью (`export`), в основном приложении ссылка идёт через прокси `/diagrams-api/...`.

**Следствия.**
* Форматы не расходятся с canvas: семантика одна и та же.
* PNG/PDF зависят от браузера пользователя (нет серверного рендера) — осознанное ограничение.
* Схема развертывания выгружается контейнерно: рамка узла с шапкой и составом внутри,
  шапка непрозрачная, тело полупрозрачное — связи между экземплярами внутри узла видны.

**Подтверждение.** `server/exporter.js` (`exportSvg`, `exportPlantUml`, `exportMermaid`,
`exportJson`, `exportDiagram`), `src/export/exportService.ts`, `src/api/exportApi.ts`.

## 5. Решения по доступу, интеграции и контрактам

### ADR-016. RBAC: матрица ролей в модуле схем; реестр авторизацию не выполняет

**Контекст.** Требования фиксируют матрицу прав по ролям; в проекте нет IAM-провайдера,
роль приходит извне.

**Решение.** Права проверяются на backend модуля схем (`server/index.js`), роль читается из
заголовка `x-user-role`, иначе берётся `DEFAULT_ROLE` (в compose — `ARCHITECT`). Матрица
`ROLE_PERMISSIONS`:

| Роль | view | edit | publish | export |
|---|---|---|---|---|
| `ADMIN` | + | + | + | + |
| `ARCHITECT` | + | + | + | + |
| `ANALYST` | + | + | — | + |
| `OWNER` | + | — | — | + |
| `OBSERVER` | + | — | — | + |

Неизвестная роль трактуется как `OBSERVER`. Текущая роль и права отдаются клиенту
(`GET /api/meta`), `403` возвращается при отсутствии права. Backend реестра (`backend/src`)
авторизацию **не** выполняет: он принимает заголовок `X-User` и использует его только как
автора изменения (ADR-017).

**Следствия.**
* Права применяются к операциям: `view` — чтение схем и валидация, `edit` — создание/правка/
  генерация/срез/восстановление версии, `publish` — публикация, `export` — выгрузка.
* Интерфейс может скрывать недоступные действия, но решение принимает сервер.
* Ограничение: авторизация реестра (кто может править объекты) реализуется вне этого проекта —
  заголовок подставляется доверенным окружением (nginx/IAM).

**Подтверждение.** `server/index.js` (`ROLE_PERMISSIONS`, `requirePermission`, `/api/meta`),
`.env.example` (`DIAGRAMS_DEFAULT_ROLE`), `backend/src/server.js` (нет проверок роли).

### ADR-017. Аудит изменений реестра — триггеры БД, автор — из заголовка `X-User`

**Контекст.** Требовался журнал изменений объектов реестра, читаемый и после удаления объекта.

**Решение.** Одна универсальная функция `fn_audit_log()` (`sql/04_audit_triggers.sql`) пишет
снимок строки до/после в `audit_log` (`old_value`/`new_value` — `jsonb`) для таблиц
`information_system`, `application_module`, `module_instance`, `project`, `information_flow`,
`information_flow_project`, `network_interface`. Автор определяется в порядке приоритета:
`app.changed_by` (значение транзакции) → `updated_by`/`created_by` строки → `session_user`.
Backend выставляет автора в транзакции: `withTransaction()` делает
`SELECT set_config('app.changed_by', $1, true)`; значение берётся из заголовка `X-User`
(percent-encoding декодируется, потому что HTTP-заголовки не переносят кириллицу).
Все изменения через API идут только через `withTransaction()` (`utils/crud.js`).

**Следствия.**
* Аудит не зависит от корректности приложения: он включён на уровне БД; «пустые» UPDATE
  (изменились только `updated_at`/`updated_by`) в журнал не пишутся.
* Триггеры `trg_touch_*` обновляют `updated_at`; `audit_log` доступен через `/api/audit`.
* Диаграммный слой модуля схем в аудит не входит (ADR-006): у схем своя история версий (ADR-014).
* Ограничение: `module_deployment`, `server`, `cluster`, `environment`, справочники и
  диаграммные таблицы в журнал не попадают — список `audited_tables` расширяется осознанно.

**Подтверждение.** `sql/04_audit_triggers.sql`, `backend/src/utils/requestContext.js`,
`backend/src/utils/crud.js`, `backend/src/routes/audit.js`, `frontend/src/utils/currentUser.ts`.

### ADR-018. Встраивание модуля «тем же origin» и двойной режим запуска

**Контекст.** Модуль схем — отдельный сервис, но пользователь не должен попадать в другое
приложение и на другой origin (иначе — CORS и второй вход).

**Решение.** nginx сервиса `frontend` (`frontend/nginx.conf`) проксирует:
* `/diagrams-api/` → `http://diagrams:3002/api/` — API модуля на том же origin, без CORS;
* `/diagrams-module/` → `http://diagrams:3002/diagrams-module/`, причём `/diagrams-module`
  без слэша отвечает `301` на путь со слэшем (иначе префикс не совпадает);
* `client_max_body_size 16m` — сохранение графа крупнее обычного JSON.
Модуль собирается с `VITE_BASE_PATH=/diagrams-module/` и `VITE_API_BASE=/diagrams-api`, а
сервер отдаёт SPA и по префиксу `APP_BASE`, и в корне своего порта (прямой доступ на 8082 и
dev-режим Vite с прокси на `localhost:3002` сохраняются). Из списка схем реестра
(`/diagrams`, страница `DiagramsPage.tsx`) редактор открывается внутренним путём
`/diagrams-module/diagrams/<id>`; ссылка «в отдельном окне» ведёт на `VITE_DIAGRAMS_URL`.

**Следствия.**
* Один вход и один origin: список схем и редактор живут внутри приложения реестра.
* Модуль остаётся самостоятельно развёртываемым: `http://localhost:8082/` работает как раньше.
* Дублирование адресов (внутренний путь и внешний порт) требует согласованности
  build-arg-ов и переменных compose — при смене префикса правятся обе стороны.

**Подтверждение.** `frontend/nginx.conf`, `docker-compose.yml` (сервис `diagrams`,
`VITE_BASE_PATH`, `VITE_API_BASE`, `DIAGRAMS_PUBLIC_URL`), `architecture-diagrams/vite.config.ts`,
`server/index.js` (`APP_BASE`), `frontend/src/utils/externalLinks.ts`, `frontend/src/pages/DiagramsPage.tsx`.

### ADR-019. Контракты API и регистро-стиль ключей

**Контекст.** PostgreSQL отдаёт `snake_case`; клиенты написаны на TypeScript в `camelCase`;
в проекте два независимых API — реестра и модуля схем.

**Решение.**
* API реестра (`backend/src`, `/api/*`) работает напрямую с колонками таблиц: тело запроса —
  `snake_case`. Клиент реестра приводит ответы к `camelCase` (`camelize`) и тела к
  `snake_case` (`snakify`), при этом заголовки собираются после spread-а `options` и через
  `Headers`, чтобы `Content-Type: application/json` не терялся.
* API модуля схем (`/api/diagrams`, `/api/registry`) отдаёт `camelCase` (сервер сам маппит
  строки БД), но выборки реестра внутри ответов (`/api/registry/*`) приходят в `snake_case`
  и приводятся к `camelCase` на клиенте; клиент модуля создан с `snakeCaseBody: false`
  из основного приложения.
* Ссылка на реестровый объект в графе — `registryRef { type, id }`, переход в карточку —
  по таблице маршрутов `REGISTRY_ROUTE` и базе `VITE_REGISTRY_URL`.

**Следствия.**
* Оба клиента используют один и тот же паттерн `createApiClient(base, { snakeCaseBody })`,
  поэтому ошибки формата тела не размножаются.
* `PUT /api/diagrams/{id}` возвращает `{ diagram, graph }` — клиент получает нормализованный
  граф (в т. ч. после применения инварианта узлов размещения, ADR-011).
* Реестр отдаёт списки «как есть» из БД — фронтенд сам отвечает за представление.

**Подтверждение.** `frontend/src/api/client.ts`, `frontend/src/api/index.ts`,
`architecture-diagrams/src/api/client.ts`, `architecture-diagrams/src/api/diagramsApi.ts`,
`server/diagrams.js` (`mapDiagramRow`), `src/config.ts` + `REGISTRY_ROUTE`.

### ADR-020. Адреса в схеме развертывания и панель «Потоки области»

**Контекст.** Схема Deployment должна отвечать на вопрос «с какого адреса на какой выполняется
поток», при этом поток в реестре описан на уровне модулей и адресов не содержит.

**Решение.** Узел размещения несёт набор адресов (`style.addresses` — из `network_interface`
владельца-сервера или владельца-кластера; *ADR-026: состав схемы — размещения среды схемы, поэтому
адреса берутся у узлов этих размещений; среда остаётся атрибутом адреса и экземпляра*).
Предпочтительный
адрес выбирается по приоритету ролей (`SERVICE → INGRESS → VIRTUAL → NODE → MANAGEMENT →
BACKUP → OTHER`, далее по возрастанию IP). Подпись связи — `адрес:порт → адрес:порт`
(`addressPairText`), при агрегации нескольких потоков — `потоков: N` и перечисление протоколов
*(изменено ADR-024: подпись связи — описание потока, адреса остаются на карточках узлов)*.
Размещения сторон вычисляет `flowDeploymentEdges` (тот же алгоритм в генераторе и в панели).
Панель «Потоки области» (`GET /api/diagrams/{id}/flows`, `server/scopeFlows.js`) показывает все
потоки области схемы: развёрнуты ли обе стороны (`deployed`), размещения сторон, `edgeIds` для
фокуса, причина («Контрагент не развёрнут в среде схемы: у модуля … нет действующего размещения»,
«Ни одна сторона потока не развёрнута в среде схемы: у модулей нет действующих размещений»,
«Связь удалена со схемы: выполните синхронизацию с реестром»)
и кнопку перехода в карточку потока реестра *(ADR-025: статусы «в срезе / вне среза» заменены
на «развёрнут / не развёрнут»; ADR-026: развёрнутость считается в среде схемы — состав панели
ограничен размещениями этой среды)*.

**Следствия.**
* Потоки, у которых контрагент не развёрнут, не теряются: они видны в панели с причиной.
* Пустые адреса фиксируются валидацией: `DEPLOYMENT_ADDRESS_MISSING` (WARNING — у узла нет
  адреса) и `EDGE_ADDRESS_UNRESOLVED` (WARNING — подпись связи без адресов);
  `ENVIRONMENT_SLICE_MISMATCH` (ERROR) — размещение относится к другой среде, чем срез схемы.
  *(изменено ADR-024: проверка подписи связи называется `EDGE_LABEL_MISSING`;
  изменено ADR-025: `ENVIRONMENT_SLICE_MISMATCH` удалена вместе с разрезом по среде, вместо неё
  появилась проверка контура сегмента `SEGMENT_MISSING`.)*
* Согласованность canvas/панель гарантируется общим построением идентификаторов связей (ADR-007).
* Ограничение: при нескольких размещениях одного модуля связь агрегируется (MVP-вариант
  «потоков: N»), детализация до отдельной физической связи выполняется вручную.

**Подтверждение.** `server/graph.js` (`loadAddresses`, `sortAddresses`, `preferredAddress`,
`addressSummary`), `server/registry.js` (`getDeploymentAddresses`),
`server/scopeFlows.js`, `server/validate.js`, `src/editor/FlowsPanel.tsx`, README модуля
*(`addressWithPort` и `addressPairText` удалены в ADR-024)*.

### ADR-023. Схема развертывания показывает только эксплуатируемое

**Контекст.** Статус объекта реестра (`PLANNED` / `ACTIVE` / `RETIRED`) — часть модели: выведенные
из эксплуатации экземпляры и серверы остаются в реестре как история. Генератор схемы развертывания
выбирал размещения по статусу **самого размещения** (`module_deployment.deployment_state = 'ACTIVE'`),
поэтому в схему попадали выведенные из эксплуатации объекты: на стенде так отображались три
экземпляра `ipkom3-runner-prod` (серверы `ipkom3-p-app-04/05/06`) и «порождаемые» ими узлы
размещения. Карточка экземпляра при этом показывала статус экземпляра (`RETIRED`) — читатель схемы
видел выведенное из эксплуатации как часть действующего ландшафта.

**Решение.**
* Размещение попадает в схему при двух условиях: `deployment_state = 'ACTIVE'` и статус всех
  участников ≠ `RETIRED` — экземпляра (`module_instance`), узла размещения (`server` / `cluster`)
  и среды (`environment`). Фильтр выполняется в SQL (`server/registry.js`: `getSystemDeployments`,
  `getModuleDeployments`), поэтому его одинаково видят генератор схемы, панель «Потоки области» и
  контур сетевого сегмента (ADR-025) — расхождений между canvas и панелью нет по построению.
* Узел размещения и контур сетевого сегмента существуют в схеме ровно потому, что внутри есть
  хотя бы одно эксплуатируемое размещение: «пустых» рамок от выведенного из эксплуатации не
  остаётся *(ADR-025: контуром схемы развертывания стал сетевой сегмент узла размещения)*.
* Карточка экземпляра модуля (C4 `DeploymentInstance`) показывает назначение модуля (`description` —
  сразу под заголовком) и код модуля (`technology`). Адрес, подпись «на узле», статус и `style.code`
  карточка экземпляра не выводит: адрес, узел и статус — атрибуты узла размещения (ADR-011, ADR-020),
  и они видны на его карточке, внутри рамки которой лежит экземпляр. В модели `style.code`,
  `style.status`, `style.role` остаются — их читают экспорт и проверки. Экспорт SVG/PlantUML приведён
  к тому же виду карточки (ADR-007, ADR-015).
* Валидация не меняется: `REGISTRY_OBJECT_RETIRED` смотрит на статус **того** объекта реестра, на
  который ссылается узел схемы. У экземпляра это ссылка на размещение (`module_deployment`, а его
  состояние — `deployment_state`, `REGISTRY_STATE_COLUMN` в `server/validate.js`), поэтому вывод из
  эксплуатации самого экземпляра (`module_instance.status`) этой проверкой не виделся: схема
  показывала выведенный из эксплуатации экземпляр как действующее размещение. Для узлов размещения
  (`server` / `cluster`) правило работает как раньше.

**Следствия.**
* Схема развертывания отвечает на вопрос «что эксплуатируется», история выводов из эксплуатации
  остаётся в реестре (и в опубликованных версиях схем).
* Поток, одна из сторон которого выведена из эксплуатации, на схеме не рисуется и объясняется в
  панели «Потоки области» причиной «Контрагент не развёрнут: у модуля … нет действующего
  размещения» (ADR-020, ADR-025).
* Схемы, сохранённые до решения, сохраняют прежний состав, пока не перестроены (`REBUILD`): в них
  выведенные из эксплуатации объекты выглядят как обычные (живой пример — опубликованная до решения
  `dep2`). Перестройка схемы развертывания — обычная реакция на изменение правил генерации
  (ADR-009, раздел 7, риск 1).

**Подтверждение.** `server/registry.js` (`getSystemDeployments`, `getModuleDeployments`),
`src/nodes/NodeShell.tsx` (`deploymentInstance`), `src/nodes/DeploymentNode.tsx`,
`server/exporter.js` (`exportSvg`, `exportPlantUml`), README модуля (разделы о схеме развертывания).

### ADR-024. Связь схемы развертывания подписана описанием потока; узел размещения — без связей и без счётчика состава

**Контекст.** Подпись связи схемы развертывания собиралась из адресов узлов
(`адрес:порт → адрес:порт`, ADR-020). Такая подпись отвечает на вопрос «откуда куда», но не
говорит, **какой поток** здесь идёт: адреса длинны, дублируют карточки узлов, а у потока есть
собственное описание в реестре (`information_flow.description`) — на стенде оно заполнено у всех
потоков. Одновременно узел размещения (C4 `DeploymentNode`) участвовал в проверке изолированных
узлов и нес в «шапке» счётчик состава: связь схемы развертывания идёт между экземплярами внутри
рамки узла (ADR-011, ADR-020), поэтому узел размещения **по построению не имеет связей** — на `di1`
это давало 5 замечаний `ORPHAN_NODE` (INFO) о норме, а счётчик дублировал то, что видно по самим
экземплярам внутри рамки.

**Решение.**
* Подпись связи схемы развертывания — описание информационного потока (`flowDescription`:
  `information_flow.description`, при пустом описании — название, затем код). Подпись собирает
  генератор (`server/graph.js`), поэтому canvas, панель «Потоки области» и все форматы экспорта
  видят одну и ту же подпись (ADR-007).
* Если в одну связь склеено несколько потоков (несколько размещений одной стороны), выводится
  описание первого и `+N` остальных; протокол и порт остаются второй строкой подписи (`technology`),
  полный состав потоков связи раскрывает панель «Потоки области» (ADR-020).
* Адреса из подписи связи убраны: адрес развертывания остается на карточке узла размещения
  (`style.addresses`, ADR-020) и в панели «Потоки области» — там, где он отвечает на вопрос «на
  каком адресе». Мёртвые после этого `addressPairText` и `addressWithPort` из генератора удалены.
* Проверка `EDGE_ADDRESS_UNRESOLVED` (WARNING — «в подписи связи нет адресов») заменена на
  `EDGE_LABEL_MISSING` (WARNING — «у связи нет описания потока»): адресов в подписи больше нет, а
  пустая подпись означает поток без описания и названия.
* Проверка `ORPHAN_NODE` не применяется к узлам размещения (`server` / `cluster`) — связь идёт
  между экземплярами, узел размещения «держит» их за состав (ADR-011). Правило есть и на backend
  (`server/validate.js`), и в предварительной проверке редактора (`src/validation/diagramValidator.ts`,
  ADR-013).
* Счётчик состава (`arch-node__count`) с карточки узла размещения убран: состав виден по экземплярам
  внутри рамки. Поле `childCount` в данных узла остаётся — оно нужно подсказке пустого тела узла;
  в экспорте строка «экземпляров: N» (`SVG`, `Mermaid`) тоже не выводится (ADR-007).

**Следствия.**
* Схема читается по смыслу: на стрелке — что за поток, на карточках узлов — где он выполняется,
  в панели — почему поток не отражён на схеме.
* Схемы, сохранённые до решения, держат прежние подписи, пока не перестроены: `SYNC` обновляет
  состав связей из реестра, сохраняя позиции, `REBUILD` дополнительно перестраивает раскладку
  (ADR-009).
* Проверка «узел не участвует в связях» перестаёт быть шумом для схем развертывания: замечания
  INFO по узлам размещения исчезают (на `di1` — 5 → 0).
* Подпись связи стала длиннее адресов, поэтому в редакторе она переносится по строкам
  (`.arch-edge__label`, `max-width`), а в SVG выводится с обрезкой — как и имена узлов.

**Подтверждение.** `server/graph.js` (`flowDescription`, `flowEdgeLabel`, `generateDeployment`),
`server/registry.js` (`getSystemFlows`, `getProjectFlows` — `fl.description`), `server/validate.js`
(`EDGE_LABEL_MISSING`, `ORPHAN_NODE`), `src/validation/diagramValidator.ts`, `src/nodes/NodeShell.tsx`,
`src/nodes/types.ts`, `src/edges/ArchitectureEdge.tsx`, `src/styles.css`, `server/exporter.js`
(`exportSvg`, `exportMermaid`), README модуля.

### ADR-025. Схема развертывания читается по сетевым сегментам; разрез по среде снят

**Контекст.** Разрез схемы развертывания по среде (ADR-010) появился, когда схема строилась
«на проект × среду»: среда выбиралась при создании схемы (`scope_environment_id`) и менялась
селектором в редакторе (`PATCH …/slice`). Практика стенда показала три следствия:

* все схемы развертывания в реестре и так созданы с фиксированной средой, поэтому вариант
  «все среды» не использовался, а селектор «Среда (все)» читался как обязательный шаг;
* контур среды (C4 `EnvironmentBoundary`) на схеме одной среды несёт ровно нулевую информацию:
  он один и охватывает всё, а вопроса «в какой среде этот узел» у читателя не возникает;
* при этом на схеме не видно измерения, которое действительно объясняет связи и адреса —
  **сетевого сегмента** (`network_segment`): сервисный адрес узла выбирается по приоритету ролей
  (ADR-020), а сегмент адреса уже читается из `network_interface.network_segment_id`.

**Решение.**
* Схема развертывания читается по уровням **«сетевой сегмент → узел размещения → экземпляр»**.
  Контур схемы — сетевой сегмент узла размещения (C4 `NetworkSegmentBoundary`): сегмент берётся у
  `network_segment_id` **предпочтительного** адреса узла (тот же приоритет ролей, что и для
  карточек узлов — ADR-020), поэтому узел с несколькими сегментами попадает ровно в один контур.
  Узел без адресов или без сегмента у адресов рисуется вне контуров.
* Разрез схемы по среде снят: `architecture_diagram.scope_environment_id` удалена
  (`server/schema.sql`: `DROP COLUMN IF EXISTS`), `updateDiagramSlice` и `PATCH /api/diagrams/{id}/slice`
  удалены, `/api/registry/environments` и селектор среды убраны из формы создания схемы
  (`frontend/src/pages/DiagramsPage.tsx`) и из тулбара редактора (`DiagramToolbar`).
  *(Уточнено ADR-026: снят именно **контур среды** и «все среды» как вариант; среда как
  параметр области схемы развертывания возвращена — колонка `scope_environment_id`,
  `PATCH /api/diagrams/{id}/environment`, `/api/registry/environments` и обязательный
  селектор среды. Контур схемы остаётся сетевым сегментом.)*
* В схему попадают действующие размещения **всех** сред: фильтр по среде убран из
  `getSystemDeployments`, `getModuleDeployments` и `getDeploymentAddresses` (`server/registry.js`).
  Среда остаётся атрибутом экземпляра и адреса и видна в панели «Потоки области».
* Панель «Потоки области» переходит от статусов «в срезе / вне среза» к «развёрнут / не
  развёрнут»: `ScopeFlow.deployed` и сводка `{ total, deployed, notDeployed, onCanvas }`
  (`server/scopeFlows.js`, `src/model/diagramTypes.ts`, `src/editor/FlowsPanel.tsx`).
* Валидация: `ENVIRONMENT_SLICE_MISMATCH` удалена вместе с механизмом разреза, вместо неё
  появилась проверка контура — `SEGMENT_MISSING` (WARNING — узел размещения не отнесён к
  сетевому сегменту). Правило реализовано и на backend (`server/validate.js`), и в
  предварительной проверке редактора (`src/validation/diagramValidator.ts`, ADR-013), а
  `ORPHAN_NODE` больше не применяется к контурам сегментов (у рамки связей не бывает).
* Экспорт рисует контур сегмента своей рамкой: в SVG — отдельный цвет и код сегмента в подписи
  контура, в PlantUML — `Deployment_Node` с кодом сегмента и зоной, в Mermaid — `subgraph`
  (рамки по-прежнему выводятся через общий признак границы, ADR-007).
* Тип C4 `EnvironmentBoundary` остаётся в модели для **ручного** контура (объект `environment`
  можно положить на схему с палитры), но генерация его больше не создаёт.

**Следствия.**
* Схема развертывания отвечает на вопрос «в каком сегменте что стоит»; среда различается по
  подписям размещений в панели и по свойствам экземпляра, а не по рамкам.
* У схем появилось измерение, которое есть на стенде: 6 сегментов (`LAN-APP` — 12 интерфейсов,
  `MGMT-01` — 6, `DMZ-APP` — 3, `DMZ-MGMT` — 1, `LAN-DB` и `VTB` — без интерфейсов), при этом у
  всех 22 интерфейсов сегмент заполнен, поэтому контуры строятся без «дыр».
* Схемы, сохранённые до решения, держат прежние контуры сред, пока не перестроены: `SYNC`
  обновляет состав и контуры, сохраняя позиции, `REBUILD` дополнительно перестраивает раскладку
  (ADR-009). Признак «одна среда» у существующих схем теряется вместе с колонкой — это осознанная
  цена решения, раздел 7 (риск 11).
* `POST /api/diagrams` больше не принимает `environmentId`; запрос с этим полем игнорируется —
  схема строится по всем средам. *(Изменено ADR-026: `environmentId` снова принимается и для
  `diagramType = 'DEPLOYMENT'` обязателен — от него зависит состав размещений.)*

**Подтверждение.** `server/graph.js` (`C4_TYPE.NETWORK_SEGMENT_BOUNDARY`, `ownerSegment`,
`loadAddresses`, `generateDeployment`, `loadScope`), `server/registry.js` (`getDeploymentAddresses`,

### ADR-026. Среда схемы развертывания — обязательный параметр области (контур остаётся сетевым сегментом)

**Контекст.** ADR-025 снял разрез схемы развертывания по среде и оставил контуром сетевой сегмент.
На стенде сразу проявился побочный эффект: схема по проекту A24-8394 (`dep4`) стала содержать
размещения **всех** сред — рядом с прод-размещениями в неё вошли тестовые (`CryptoPro Test` на
сервере `vql-kom3csp01`, `mail.life.rgs.local-test`, `ipkom3-runner-k8test` на кластере
`ipkom3k8S-test`) и узлы, у которых кроме тестовых размещений ничего нет (сервер `vql-kom3csp01`).
Читатель прод-схемы видел в ней тестовый ландшафт, а признака «эта схема — про PROD» в данных не
осталось (раздел 7, риск 11 в прежней редакции). Среда — существенное измерение схемы
развертывания: размещение всегда относится к одной среде (`module_instance.environment_id`), а
различить прод и тест по карточке размещения (`style.environmentCode`) можно только «глазами» —
узлы без прод-размещений из схемы при этом не исчезают.

**Решение.**
* Среда — обязательный параметр области схемы развертывания, наравне с объектом области
  (`scope_type` / `scope_object_id`): колонка `architecture_diagram.scope_environment_id`
  возвращается идемпотентной миграцией (`ADD COLUMN IF NOT EXISTS`). Для
  `diagram_type = 'DEPLOYMENT'` среда обязательна: `POST /api/diagrams` отвечает 400 без
  `environmentId`, 404 — если среды нет, 400 — если среда `RETIRED`; у схем контекста и
  контейнеров значение не заполняется и снимается миграцией.
* Варианта «Все среды» нет: схема описывает размещения **одной** среды. Выборка размещений
  фильтруется по среде схемы в SQL (`server/registry.js`: `getSystemDeployments`,
  `getModuleDeployments` — третий параметр `environmentId`), поэтому в схему не попадают ни
  размещения других сред, ни узлы, у которых размещений выбранной среды нет.
* Контур схемы остаётся сетевым сегментом (ADR-025): среда — измерение **состава**, сегмент —
  измерение **рамки**. Контуры среды (`EnvironmentBoundary`) по-прежнему генерацией не создаются
  и остаются только для ручного контура с палитры.
* Смена среды у существующей схемы — `PATCH /api/diagrams/{id}/environment` (право `edit`):
  среда сохраняется, граф перестраивается полностью (`REBUILD`), потому что меняется состав
  размещений — ручная раскладка предыдущей среды не переносится (ADR-009). Опубликованная схема
  возвращается в `DRAFT` (ADR-014).
* Версия фиксирует среду: `snapshot.scope.environmentId`; восстановление версии возвращает и
  среду версии — иначе граф описывал бы состав одной среды, а карточка схемы — другой.
* Валидация: `ENVIRONMENT_SCOPE_MISSING` (ERROR — у схемы развертывания не выбрана среда: состав
  недостоверен, публикация блокируется) и `ENVIRONMENT_SCOPE_MISMATCH` (WARNING — размещение на
  схеме относится к среде, отличной от среды схемы, например узел добавлен вручную с палитры).
  Правила реализованы и на backend (`server/validate.js`), и в предварительной проверке редактора
  (`src/validation/diagramValidator.ts`, ADR-013).
* Панель «Потоки области» считает развёрнутость сторон в среде схемы
  (`server/scopeFlows.js` → `getModuleDeployments(..., environmentId)`), причины формулируются как
  «Контрагент не развёрнут в среде схемы: …».
* UI: среда выбирается при создании схемы развертывания (форма создания в модуле и в реестре) и
  меняется селектором «Среда схемы» в тулбаре редактора; список схем показывает колонку «Среда»,
  подпись схемы и подпись экспорта — код среды (`DEPLOYMENT · dep4 · PROD`).

**Следствия.**
* Схема развертывания отвечает на вопрос «что и где развёрнуто **в этой среде**»: тестовый
  ландшафт больше не подмешивается в прод-схему. Для второй среды нужна вторая схема (или смена
  среды у существующей) — это и есть практика стенда, где каждая схема создавалась под одну среду
  (ADR-025, контекст).
* Измерения разделены: среда — состав, сетевой сегмент — контур; обе оси читаются независимо
  (прод-схема по-прежнему показывает сегменты `LAN-APP`, `MGMT-01`, …).
* Схемы развертывания, созданные при снятом разрезе (на стенде — `dep4`, `Dep3`, `di1`, `dep2`),
  после миграции остаются без среды: они помечаются `ENVIRONMENT_SCOPE_MISSING` (ERROR) и не
  публикуются, пока среда не выбрана в тулбаре редактора (или через `PATCH …/environment`).
  `dep4` и `di1` на стенде переведены на `PROD` (раздел 6).
* Узел, у которого есть размещения только других сред, из схемы исчезает вместе со своими
  адресами: сервер `vql-kom3csp01` (единственное размещение — тестовое) в прод-схеме не рисуется.

**Подтверждение.** `server/schema.sql` (`scope_environment_id`, идемпотентная миграция),
`server/registry.js` (`listEnvironments`, `getSystemDeployments`, `getModuleDeployments`),
`server/diagrams.js` (`requireActiveEnvironment`, `createDiagram`, `updateDiagramEnvironment`,
`getDiagramGraph`, `listDiagrams`, `publishDiagram`), `server/graph.js` (`loadScope`,
`generateGraph`, `generateDeployment`), `server/index.js` (`GET /api/registry/environments`,
`PATCH /api/diagrams/{id}/environment`, `POST /api/diagrams/:id/generate`, экспорт),
`server/scopeFlows.js`, `server/validate.js` (`ENVIRONMENT_SCOPE_MISSING`,
`ENVIRONMENT_SCOPE_MISMATCH`), `server/exporter.js`, `src/api/diagramsApi.ts`,
`src/api/registryApi.ts`, `src/model/diagramTypes.ts`, `src/editor/DiagramToolbar.tsx`,

несуществующей средой → 404, с не-uuid → 400; `POST` для `CONTAINER` без среды → 201 (среда не
заполняется); `PATCH …/environment` у схемы контейнера → 400. Схема, созданная через
`POST /api/diagrams` со средой `PROD` (авто-`REBUILD`), сразу даёт прод-состав (11 узлов / 4 связи)
и удаляется без следов.

Наблюдение (не связано со средой): в раскладке `REBUILD` рамка контура `LAN-APP` и узел
`Adinsure Prod` получают одинаковую позицию `(80, 80)` — узел внутри рамки, но вплотную к её
левому верхнему углу (у остальных узлов контура позиции разнесены). Это поведение раскладки
(`server/layout.js`), тема отдельного улучшения; на состав и валидацию схемы не влияет.

## 7. Риски и технический долг

| № | Риск / долг | Влияние | Что предлагается |
|---|---|---|---|
| 1 | Опубликованные до ADR-011 схемы сохраняют старое «плоское» расположение (`dep2`) | схема читается неверно, валидация даёт WARNING-и | перестроить такие схемы (`REBUILD`) и закрепить в регламенте: после изменения правил раскладки схемы перестраиваются |
| 2 | Узлы размещения без адресов (`DEPLOYMENT_ADDRESS_MISSING`) | подпись связи не отвечает на вопрос «с какого адреса на какой» | заводить адреса в реестре (`network_interface`), а не в схеме |
| 3 | Авторизация реестра отсутствует: `X-User` приходит от клиента и подставляется доверенным окружением | при прямом доступе к API автора изменения можно подделать | подключить IAM/прокси с подписью заголовка, ограничить доступ к порту 3001 |
| 4 | Пустой корневой `README.md` при работающей системе | новичку негде прочитать «как запустить всё вместе» | перенести в корневой README краткий запуск или сослаться на модульные README и этот ADR |
| 5 | Правила геометрии продублированы: `server/layout.js`, `src/layout/layoutService.ts`, `server/exporter.js` | правка правила требует синхронного изменения трёх мест, иначе canvas ≠ экспорт | сохранять пометки «совпадает с …» (уже есть) и проверять все три слоя при изменении правила |
| 6 | Протокол замечаний к ТЗ v1.0 не согласован (16 замечаний, Б1–Б4) | объём новой доработки схем развертывания не зафиксирован | закрыть Б1–Б4 решениями из ADR-002…004 и ADR-022, выпустить ТЗ v1.1 |
| 7 | `diagram_version` не участвует в аудите, снапшот не индексируется | сложно искать «в какой версии было иначе» | при необходимости — отчёт по версиям, без изменения модели |
| 8 | Отчёты и схема читают БД независимо (нет общего сервиса разбора адресов) | при изменении семантики адресов правки в двух местах | при появлении третьего потребителя вынести разбор адресов в представление или общий модуль |
| 9 | Схемы, сохранённые до ADR-023, показывают выведенные из эксплуатации объекты (на стенде — `dep2` и `di1` до перестройки) | схема отвечает на вопрос «что когда-то разворачивалось», а не «что эксплуатируется»; валидация такие узлы не помечает: экземпляр в схеме ссылается на размещение (`deployment_state`), а не на модуль | перестраивать схемы развертывания после выводов из эксплуатации (`REBUILD`), для `PUBLISHED` — новым выпуском версии (ADR-014) |
| 10 | В реестре есть значения с невидимыми символами (сервер `vpl-kom3csp01` + U+2008) | подпись узла на схеме и в экспорте выглядит обрезанной, сравнение имён «глазами» обманывает | исправить значение в реестре при ближайшей инвентаризации; при импорте данных — проверка на управляющие и непечатаемые символы |
| 11 | Схемы развертывания, созданные при снятом разрезе по среде (на стенде `dep4`, `Dep3`, `di1`, `dep2`), после ADR-026 остаются без среды | схема не публикуется: `ENVIRONMENT_SCOPE_MISSING` (ERROR) — состав размещений не определён | выбрать среду в тулбаре редактора (`PATCH /api/diagrams/{id}/environment`): граф перестраивается, схема возвращается в `DRAFT` (ADR-014). Автоматически определить «среду» существующей схемы нельзя: одни и те же модули проекта могут иметь размещения в нескольких средах |
| 12 | Среда схемы обязательна, но у выбранной области может не быть размещений в этой среде | схема получается пустой: размещений нет — нет узлов, контуров и связей | среда выбирается из списка действующих сред реестра (`GET /api/registry/environments`), а пустой состав объясняет панель «Потоки области» причинами «Контрагент не развёрнут в среде схемы» |
