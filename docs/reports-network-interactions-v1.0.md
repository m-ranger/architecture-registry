# Отчёт «Сетевые взаимодействия» (раздел «Отчеты»)

**Дата:** 08.10.2026
**Раздел приложения:** «Отчеты» → «Сетевые взаимодействия»
**API:** `GET /api/reports/network-interactions` (`backend/src/routes/reports.js`)

## Назначение

Отчёт отвечает на вопрос **«с какого адреса на какой» выполняется каждый
информационный поток реестра**: поток описан на уровне модулей (`information_flow`),
а адрес стороны выводится из размещения экземпляра модуля —
`module_instance` → `module_deployment` → `server` / `cluster` → `network_interface`.

Отчёт — производное представление тех же данных, что и схемы развертывания (ТЗ §10.3):
приоритет роли адреса совпадает с `v15a_instance_primary_address`
(`SERVICE` → `INGRESS` → `VIRTUAL` → `NODE` → `MANAGEMENT` → прочие), поэтому
адрес в отчёте и адрес на узле/связи схемы совпадают.

## Модель строки

Строка отчёта — сочетание размещений сторон потока (по одному размещению на
экземпляр модуля в среде), поэтому для модуля, развернутого на нескольких узлах,
получается несколько строк — по одной на каждый адрес.

## Правило «одна среда на поток»

Поток не может идти из одной среды в другую: **Test показывается только на Test,
Prod — на Prod**. Если у обеих сторон известны среды и они разные, пара в отчёт не
попадает — раньше в отчёте была, например, строка `DEV → PROD` для потока
`01-test ЛКК`. Правило задано условием `SAME_ENVIRONMENT_SQL` и согласовано с
`v16_flow_addresses`, где стороны соединяются по `module_instance.environment_id`.

Скрытые пары не теряются бесследно: API возвращает их количество и разбивку по
парам сред в поле `excluded`, а интерфейс показывает предупреждение и счётчик в
заголовке списка.

Пара, у которой среда одной из сторон неизвестна (нет экземпляра, размещения или
адреса), правило не нарушает и остаётся в отчёте с пометкой — так видно, где не
хватает данных реестра.

| Колонка | Источник |
|---|---|
| Информационный поток | `information_flow.code`, `name`, `status`, коды проектов (`information_flow_project`) |
| Протокол / порт | `protocol.code`, `COALESCE(flow.target_port, protocol.default_port)` |
| Среда | среда обеих сторон (`environment.code`) — по правилу «одна среда на поток» она совпадает, «не определена» означает незаведённое размещение |
| Источник — с какого адреса | ИС и модуль-источник, экземпляр, среда, узел размещения (сервер/кластер), предпочтительный адрес |
| Получатель — на какой адрес | то же для модуля-приёмника |

## Поведение на неполных данных

Стороны соединены `LEFT JOIN`, поэтому поток остаётся в отчёте, даже если данных
не хватает: строки с пустым адресом помечаются в интерфейсе как
**«адрес не зарегистрирован»** и **«размещение не задано»**. Это осознанное решение:
представление `v16_flow_addresses` использует `INNER JOIN` и на базе, где адреса или
размещения ещё не заведены, вернуло бы пустой результат (замечания У9/Б4 протокола
`docs/requirements-review-deployment-diagrams-v1.0.md`).

## Фильтры

| Параметр | Значение |
|---|---|
| `source`, `target` | сторона потока: `addr:<ip>` (адрес), `node:<узел>` (сервер/кластер), `instance:<экземпляр>`, `module:<код ИС>/<код модуля>`, `none` (адрес не зарегистрирован) |
| `environment` | код среды (`PROD`, `TEST`, `DEV`, `QUA`) — учитываются обе стороны потока |
| `statuses` | состояния потока через запятую; по умолчанию `ACTIVE,PLANNED` (как в `v16_flow_addresses`) |
| `project` | код проекта: потоки, задействованные в проекте |
| `q` | поиск по коду и наименованию потока |

Ответ: `{ total, rows, excluded, options, applied }`. `rows` — строки отчёта,
`excluded` — пары, скрытые правилом «одна среда на поток»:
`{ "crossEnvironment": 6, "pairs": [{ "sourceEnvCode": "DEV", "targetEnvCode": "PROD", "total": 2 }, …] }`,
`options` — варианты фильтров «Источник», «Получатель», «Среда», «Проект» и
«Состояние потока». Варианты источника и получателя считаются без фильтров стороны,
среды и поиска, чтобы список выбора не «схлопывался» после применения фильтра.

```bash
# Все взаимодействия с адреса 10.10.10.100
curl "http://localhost:8080/api/reports/network-interactions?source=addr:10.10.10.100"

# Потоки проекта A24-8394, у которых у получателя адрес не зарегистрирован
curl "http://localhost:8080/api/reports/network-interactions?project=A24-8394&target=none"
```

## Пример (данные реестра от 08.10.2026)

После применения правила в отчёте 10 строк (до правила было 16: скрыто 6 пар из
разных сред — `DEV → PROD` 2, `DEV → TEST` 1, `PROD → TEST` 2, `TEST → PROD` 1).
Адреса выводятся для развернутых узлов, остальное помечается:

| Поток | Среда | Источник | Получатель |
|---|---|---|---|
| `NFS-1` (`NFS:2049`) | не определена | `ADS/ADS-APP` — размещение не задано | `NFS/NFS` — размещение не задано |
| `NFS-2` (`NFS:2049`) | PROD | `ipkom3/runner` — кластер `ipkom3k8-prod` `10.10.10.100` (INGRESS) и сервер `ipkom3-p-app-04` `10.10.10.14` (SERVICE) | `NFS/NFS` — размещение не задано |
| `NFS-2` (`NFS:2049`) | TEST | `ipkom3/runner` — кластер `ipkom3k8S-test` `10.10.10.150` (INGRESS) | `NFS/NFS` — размещение не задано |
| `NFS-3` (`HTTPS:8090`) | PROD | `ipkom3/runner` — `10.10.10.100`, `10.10.10.14` | `CRYPT/CRYPT1` — размещение не задано, адрес не выводится |
| `NFS-3` (`HTTPS:8090`) | TEST | `ipkom3/runner` — `10.10.10.150` (INGRESS) | `CRYPT/CRYPT1` — сервер `vql-kom3csp01` `10.228.237.124` (UPLINK) |
| `NFS-4` (`SMTP:587`) | PROD | `ipkom3/runner` — `10.10.10.100`, `10.10.10.14` | `MAIL/MAIL` — размещение не задано |
| `NFS-4` (`SMTP:587`) | TEST | `ipkom3/runner` — `10.10.10.150` (INGRESS) | `MAIL/MAIL` — размещение не задано |

Поток `01-test ЛКК` (`LKK2/test lkk` в DEV → `ipkom3/runner` в PROD и TEST) в отчёт
не попадает: это пара из разных сред, то есть ровно тот случай, который правило
исключает.

## Ограничения

* фильтр по стороне сравнивает адрес без маски подсети (`host(ip_address)`), так как
  `network_interface.ip_address` объявлен как `inet`;
* сетевой контур (зона/сегмент) выводится только при заполненном `network_segment_id`
  у адреса;
* раздел «Отчеты» также содержит «Матрицу информационных потоков» (`/matrix`) — она
  строится на данных реестра через `GET /api/reports/flow-matrix`
  (см. `docs/reports-flow-matrix-v1.0.md`);
* экспорт отчёта в файл (CSV/XLSX) не реализован.
