# «Матрица информационных потоков» (раздел «Отчеты»)

**Дата:** 08.10.2026
**Раздел приложения:** «Отчеты» → «Матрица информационных потоков» (`/matrix`)
**API:** `GET /api/reports/flow-matrix` (`backend/src/routes/reports.js`)

## Назначение

Матрица отвечает на вопрос **какие модули с какими обмениваются информационными
потоками**: строка — модуль-источник, столбец — модуль-назначение, ячейка — потоки
между парой модулей. В ячейке — коды потоков, в подсказке — наименование, протокол с
портом, состояние и проекты потока.

Это то же производное представление, что и `v05_information_flow_matrix`
(раздел 14 ТЗ), но собранное из `information_flow` + `application_module` +
`information_system`: представление не содержит идентификаторов модулей и сред их
экземпляров, поэтому на нём нельзя было бы фильтровать матрицу и связывать её с
карточками реестра.

Диагональ матрицы пуста: поток модуля «сам в себя» запрещён (REQ-020) — так же, как
в `v16_flow_addresses` (`sm.id <> tm.id`).

## Оси и ячейки

| Что | Откуда |
|---|---|
| Ось (строка и столбец) | `application_module` + `information_system.code`; среды экземпляров — `module_instance` → `environment.code` |
| Ячейка | `information_flow` (пара `source_module_id` / `target_module_id`) |
| Протокол и порты | `protocol.code`, `COALESCE(flow.source_port, protocol.default_port)`, `COALESCE(flow.target_port, protocol.default_port)` |
| Проекты потока | `information_flow_project` → `project.code` |

Оси и ячейки запрашиваются раздельно (`modules` и `flows` в ответе), клиент
группирует потоки по паре «источник → назначение». Модуль, участвующий в отобранном
потоке, всегда попадает в оси, даже если он выведен из эксплуатации — иначе поток
«потерялся» бы в матрице.

## Фильтры

| Параметр | Значение |
|---|---|
| `statuses` | состояния потока через запятую; по умолчанию `ACTIVE,PLANNED` |
| `project` | код проекта: потоки, задействованные в проекте |
| `is` | код ИС: матрица внутри одной информационной системы (обе стороны потока в ней) |
| `q` | поиск по коду и наименованию потока |
| `onlyInvolved=1` | только модули, между которыми есть отобранные потоки |
| `includeRetired=1` | показывать выведенные из эксплуатации модули |

Фильтр `is` отбирает **потоки внутри ИС**: и источник, и назначение потока должны
принадлежать выбранной системе, поэтому матрица остаётся квадратной (такие потоки
всегда дают заполненные ячейки на своих осях). Практическое следствие: если все
потоки системы идут на модули других систем, матрица будет пустой, хотя потоки у
системы есть — в реестре от 08.10.2026 `is=NFS` даёт 1 ось (`NFS`) и 0 потоков,
потому что `NFS-1` (`ADS-APP → NFS`) и `NFS-2` (`runner → NFS`) пересекают границы
ИС. Чтобы увидеть их, фильтр по ИС нужно снять.

## Примеры запросов

```bash
# Вся матрица по активным и планируемым потокам
curl "http://localhost:8080/api/reports/flow-matrix"

# Матрица внутри одной информационной системы
curl "http://localhost:8080/api/reports/flow-matrix?is=CRYPT"

# Только модули, участвующие в потоках проекта A24-8394
curl "http://localhost:8080/api/reports/flow-matrix?project=A24-8394&onlyInvolved=1"
```

`ADS-APP`, `CRYPT1`, `MAIL`, `NFS`, `runner`, `test lkk`).

## Ограничения

* правило «одна среда на поток» отчёта «Сетевые взаимодействия» здесь не
  применяется: матрица логическая, она связывает модули, а не адреса в средах; среды
  экземпляров модуля отдаются справочно в `env_codes`;
* демонстрационные данные `frontend/src/mock` страницей больше не используются — она
  работает только на данных реестра (остальные страницы приложения — вне этой задачи);
* экспорт матрицы в файл (CSV/XLSX) не реализован;
* состояния берутся из `information_flow.status`; состояния модулей влияют только на
  состав осей (`includeRetired`).
